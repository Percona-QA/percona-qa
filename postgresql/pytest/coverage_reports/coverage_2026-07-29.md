### Headline

PITR is no longer covered only by a thin cold-copy module. The suite now mirrors operator reality:

1. **Core PG + TDE wrappers** — file archive + cold `$PGDATA` copy  
2. **Physical basebackup** — `pg_basebackup` / `pg_tde_basebackup -E` as the base image  
3. **pgBackRest** — stanza/repo restore with `--type=time|lsn|xid`, backup chains, encrypted-in-repo, and repo sabotage negatives  

Overlapping scenario names (time/LSN/XID, exclusive, pause, DROP, missing WAL) are intentional: they guard **different integration surfaces**, not identical code paths.

## 1. How the three PITR modules differ

| | `test_pitr.py` | `test_pg_basebackup.py` | `test_pg_tde_pgbackrest.py` |
|---|---|---|---|
| **Base image** | Cold `copytree` of PGDATA | `pg_basebackup` / `pg_tde_basebackup -E` | `pgbackrest backup` → `restore` |
| **WAL archive** | `cp` or TDE decrypt wrappers → file dir | Same file-archive style | pgBackRest repo (`archive-push` / `archive-get`) |
| **Recovery config** | Hand-written `postgresql.auto.conf` + `recovery.signal` | Same on copied basebackup | pgBackRest `--type` / `--target*` / `--target-exclusive` / `--set` |
| **Proves** | Core recovery + TDE archive wrappers | PITR when base is a real basebackup | PITR through the backup tool (chains, repo, ciphertext-in-repo) |
